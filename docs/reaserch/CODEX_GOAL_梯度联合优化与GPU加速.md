# Codex Goal：改善跨 MFFC 梯度联合优化的质量—时间权衡

日期：2026-11-13

## 1. 总目标与研究主线

在现有 MFFC 分区、候选提取、冻结 LiteCut、可微代理、真实 rewrite/CEC/ABC mapping 闭环上继续改进，实现：**以较低的端到端运行时间，获得有竞争力的 mapping 后 critical delay，并通过实验区分梯度联合选择和 GPU 并行各自的贡献。**

不是要求每个电路的 delay 都超过 ABC，也不是单纯追求某个 GPU kernel 的最大加速比。核心是可复现的 Delay–Runtime trade-off；质量不能严重退化，算法创新也不能只由“用了 Adam、STE 或 GPU”来代替。

保持主线：

**MFFC 组织决策空间 → LiteCut 提供局部信息 → 轻量可微目标指导跨 MFFC 联合选择 → 安全地利用 GPU 并行 → 真实 rewrite、CEC、ABC mapping/timing 验证。**

不把研究重心重新转回精确重建每条 PI→PO 时序或训练大型全局预测器。允许为了优化有效性而对辅助代理作必要的小规模调整。

## 2. 现状与工作方式

先阅读 `GRADIENT_OPTIMIZATION_STATUS.md` 并对照实际代码、配置和日志，保留当前可复现实验版本。现有结果是诊断起点，不是必须保留的算法设计。

当前已知：梯度闭环可运行，但代理下降尚不能可靠对应真实 delay 改善；直接梯度提案存在较多执行失败；同预算随机对照尚无稳定优势；主实验的候选梯度更新运行在 CPU float64。不要未经诊断就将这些问题归咎于 Adam 或 STE。

本轮是算法与实现改进任务，不是再做一次全仓库测试覆盖审计。复用已有验证基础，把精力用于能改善实际搜索效率与端到端性能的环节。

## 3. 三条工作主线

### A. 先明确评价口径和主要瓶颈

建立当前版本的质量—时间基线，并判断限制主要来自候选评价、梯度方向、离散选择/冲突处理、真实安装、GPU 利用率，还是重复真实工具调用。根据证据安排优先级，不预设必须替换哪个模块。

### B. 提高梯度联合选择的实际效率

目标是在有限时间与评价资源下，更容易提出可执行且有实际时序收益的候选组合，减少无效尝试。保留跨 MFFC 的联合性，不能把各 region 独立贪心的批处理称为联合梯度优化。

具体的选择表示、更新策略、辅助代理、冲突处理、反馈方式和停止条件由你依据证据选择。默认先沿用现有方法；只有诊断支持时才替换基础算法，并保留受控对照。不要单靠增加搜索预算、增加真实 mapping 次数或叠加既有 ABC 优化流程制造收益。

### C. 实现有实际收益的 GPU 并行

围绕单个电路内部的 MFFC/候选组织，找出真正值得并行的计算并实现加速；区分已有 CULS 等项目提供的能力与你新增的部分。

MFFC 节点不重叠不代表时序独立或所有 rewrite 可无条件并发。保留依赖、冲突和完整安装检查，允许合理的 CPU/GPU 协作。不强制所有阶段上 GPU，也不能将多个 benchmark 的并发吞吐当成单电路优化延迟的降低。

## 4. 评价原则

- **真实质量：** 统一输入、ABC 版本、Liberty、mapping/timing 配置和功能等价条件；区分 original 与 replay no-op。面积约束/评价方式在比较前明确并冻结。Delay 为主线，joint 模式单独作为扩展，不能混用两种目标的成绩。
- **整体竞争力：** 重点比较相同时间下的最好已验证 delay，以及达到预先约定质量所需的时间；同时保留同请求预算比较来分析搜索效率。报告逐设计结果和不同规模/来源的分组结果。
- **贡献分离：** 参照原图 mapping、native ABC rewrite、LiteCut 贪心、同预算随机、当前框架及适用的 CULS/GPU 原流程。用必要的消融与同算法 CPU/GPU 对照，区分梯度、LiteCut/交互信息、修复和并行实现的贡献。
- **完整成本：** 端到端计时包含实际部署需要的初始化、特征/候选准备、推理、校准、数据传输、选择、失败/修复、CEC 和所有在线 mapping/timing 调用；可另报算法时间、内核时间和冷/热启动，但不能互相替代。请求数、实际工具调用数和缓存复用分开记账。
- **公平性：** 核对基线编译优化、硬件、线程/worker 数、精度及缓存条件；CPU/GPU 同算法比较要检查数值和最终 QoR。开发与最终评估分开，避免按结果挑选电路；在固定评估上检查随机性与重复性。现有 905 个已分析电路不能自动声称是未见测试集。
- **正确性：** 不混用 MIO 与 Liberty 标签，不使用已撤回标签，不把部分安装结果当完整组合成功；预测先于实测标签保存。失败、超时、无改善和 no-op 如实保留，修复后的收益注明来源。

## 5. 备选算法的使用边界

参考随附的 `评价体系与备选算法_文献记录.md`。新文献中的梯度估计器、离散更新策略及 GPU 技术先留作备选，不要求全部实现。

若决定启用备选，先说明它针对已观察到的哪个瓶颈，再用小范围受控对照判断收益是否值得其新增成本。采用已有算法应明确引用，不能作为原创算法宣称。

## 6. 完成标准与交付

交付可复现的改进版本、必要的测试与实验记录，以及一份简明报告，回答：

1. 当前最主要的瓶颈是什么，做了哪些有依据的改变？
2. 在统一条件下，实际 delay、面积、端到端 runtime 和有效提案率怎样变化？
3. 梯度与 GPU 分别带来什么收益，哪些收益仍未证明？
4. 哪些电路/规模有效，哪些失败或退化，下一步最值得解决什么？

成功不是 loss 更低、测试更多或 GPU 使用率更高，而是：**在可接受的真实 QoR 下减少时间，或在相同时间内找到更好的真实结果，并有证据解释提升来自哪里。**“可接受的 QoR”及面积口径应在最终比较前固定，不能根据结果事后改变。

若尚无优势，交付负结果与原因，不修改评价口径掩盖问题。具体实现方案、算法细节和实验推进顺序由你自主决定。
